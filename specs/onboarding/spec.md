# Spec: Onboarding Generator | Spec ID: SPEC-02 | Status: approved

## Problem and why

Someone new to a repository needs the same things every time: what it is, how the
pieces connect, how to run it, which files matter and in what order to read them.
Written by hand, that page goes stale; generated by a model from raw files, it is
expensive and invents paths. The tour is built the map-reduce way: code collects every
fact it can for free, and one model call turns those facts into prose.

## Goals / Non-goals

Goals
- A five-section tour per repository: architecture, critical paths, how to run, a
  reading path, first tasks.
- Facts from the git tree, the index and the package manifests; one model call for the
  narrative.
- A useful tour even without a model: a skeleton built from the facts.

Non-goals
- Answering questions about the repo (agentic search) — this is a batch document.
- Reading source files, Docker or CI files to explain them (their presence is a fact,
  their content is not read).
- Sharing links, scheduled regeneration, languages other than English.

## User stories

- As a new contributor, I open Onboarding Tour and see how the system is put together
  and which files to read first.
- As the person who set DevDigest up, I regenerate the tour after a big refactor.
- As a cost-conscious user, I see what the tour cost and which model wrote it — or that
  no model was involved.

## Acceptance criteria (EARS)

Facts (no model)
- **AC-1** WHEN a tour is generated, the system shall count the committed files per
  language (by extension) and per top-level directory from the git tree.
- **AC-2** WHEN a tour is generated, the system shall take from the `package.json` files
  their package name, scripts and the dependencies it recognises as frameworks, and the
  package manager from the lockfiles present.
- **AC-3** WHEN a tour is generated, the system shall note which of Dockerfile, a Compose
  file, an env example and CI workflows exist, by path only.
- **AC-4** WHEN a tour is generated, the system shall take from the index the endpoints
  and cron jobs, the top-ranked files and the import chains from them; WHERE the index
  has none of these (it parses only JS/TS), those facts are empty and the tour says so.
- **AC-5** The system shall read file contents only for `package.json` files: at most
  ten, the shallowest first, each at most 64 KB; it shall ignore one that is not valid
  JSON and never follow a symbolic link.
- **AC-6** The facts sent to the model shall not exceed 24,000 characters; lists are
  trimmed to their top entries to fit.

Narrative (one model call)
- **AC-7** The system shall make at most one model call per generation, with the facts as
  its only repository input, inside one untrusted block, under fixed instructions that
  say the block is data.
- **AC-8** The tour shall have exactly five sections in this order: `architecture`,
  `critical_paths`, `how_to_run`, `reading_path`, `first_tasks`; only `architecture`
  may carry a diagram.
- **AC-9** The reading path shall be the top-ranked files of the index (at most eight,
  rank descending, ties by path), in that order; the model's notes are attached to those
  steps, and a step or path the model adds is ignored.
- **AC-10** The critical paths shall be the import chains from the index; the model's
  notes are attached to them, and a path the model adds is ignored.
- **AC-11** IF the model output links a path that is not a committed file, THEN the
  system shall drop that link.
- **AC-12** The system shall remove links and images from model-written Markdown; the
  only file links in a tour are the ones the server builds from validated paths.
- **AC-13** The system shall store with the tour the model, the cost of the call, the
  generation time and the indexed commit the facts came from.

Fallback, state, errors
- **AC-14** IF the model call fails, returns output that does not match the schema,
  takes longer than 90 s, or no provider has a key, THEN the system shall produce a
  skeleton tour from the facts alone, marked as a skeleton with the reason and a null
  cost.
- **AC-15** IF a model-written tour is stored and regeneration falls back to a skeleton,
  THEN the system shall keep the stored tour and report that regeneration failed.
- **AC-16** IF repo-intel is off or the repository has no completed index (status
  `full` or `partial` with an indexed commit), THEN the system shall refuse to generate
  with 409 and say to index it first.
- **AC-17** IF a generation for the repository is already running, THEN the system
  shall refuse a second one with 409.
- **AC-18** WHEN a stored tour exists, the system shall return it without a model call.
- **AC-19** WHEN the user regenerates and it succeeds, the system shall replace the
  stored tour.

UI
- **AC-20** WHILE no tour is stored, the Onboarding Tour page shall show an empty state
  with a Generate button.
- **AC-21** The page shall show the sections in order with an "on this page" index, and
  every file link shall open the file on GitHub at the indexed commit.
- **AC-22** The page footer shall name the model, the cost and the indexed commit, or say
  that the tour is a skeleton and why.
- **AC-23** The page shall render section Markdown without raw HTML, and draw the
  architecture diagram only if it parses as Mermaid.

## Edge cases

- No `package.json`: how-to-run lists what exists (Compose, Dockerfile) or says nothing
  was found.
- A monorepo with many manifests: root and one level down first, ten at most (AC-5).
- An index with no import edges (non-TS repos): critical paths empty, reading path from
  rank only; ranks all equal → path order (AC-9 tie rule).
- A script name or file path written to look like instructions: it stays inside the
  untrusted block and cannot change the sections (AC-7, AC-8).

## Non-functional

- Cost: one call with at most ~6K tokens of facts; under $0.01 on the default model.
- The tour is cached per repository; opening the page is free (AC-18).

## Inputs (provenance)

- [deterministic: git] committed files with modes and sizes; up to ten `package.json`
  read from the commit.
- [deterministic: repo-intel] index state, ranked files, import chains, endpoints and
  crons per file.
- [reused: SPEC-01] context documents list (paths only).
- [new: 1 LLM call] the narrative, feature model `onboarding`.

## Untrusted inputs

Manifest names, script commands, file paths and document paths come from the
repository. They go to the model only as JSON facts inside one `<untrusted>` block
(reviewer-core's wrapper, which stops the content from closing the block), with the
system rule that the block is data (AC-7). The model's output is constrained by a
schema and then grounded by the server: fixed sections and order (AC-8), steps and
chains from the index (AC-9, AC-10), unknown paths dropped (AC-11), no links or images
in prose (AC-12). The UI renders Markdown without raw HTML (AC-23).

## Open questions

None open. Decided: English only; diagram only in `architecture`; the starter prompt
template (`onboarding.system.md`, which asked for a `routes_and_apis` section and file
excerpts) is rewritten to match AC-7–AC-10.
