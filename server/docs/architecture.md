# Server architecture

How a request travels through the API and where each kind of code belongs.

## Boot

`src/server.ts` calls `buildApp()` (`src/app.ts`) and listens. `buildApp` is also
what tests use — they call `app.inject()` instead of opening a port.

Order inside `buildApp` matters:

1. Fastify instance with a 1 MB body limit and pino logging.
2. `fastify-type-provider-zod` compilers, so zod schemas validate requests and
   serialize responses.
3. The DI `Container` is created and decorated onto the app (`app.container`).
4. Orphaned runs are reaped **before** the server accepts requests: any
   `agent_runs` row still `running` belongs to a dead process and is marked
   `failed`. This is awaited so a fresh run can never be reaped by mistake.
5. Plugins — helmet, CORS (`WEB_PORT` origin), global rate limit (120/min, off in
   tests, tighter on `POST /pulls/:id/review`), SSE.
6. Feature modules from `src/modules/index.ts`, registered statically (dynamic
   `import()` of `.ts` is not portable across tsx, the bundler and vitest).
7. The error handler: zod validation → 422, `AppError` → its status, response
   serialization failure → 500, all in one `ApiErrorBody` envelope.

## Dependency injection

`src/platform/container.ts` holds config, the Drizzle `db`, the `JobRunner`, the
SSE `RunBus` and lazily built adapters:

| Getter | Adapter | Notes |
|---|---|---|
| `llm(id)` | OpenAI / Anthropic / OpenRouter | built from the secret key on first use, cached; `invalidateSecretCaches()` after a key changes |
| `github()` | Octokit | throws `ConfigError` without `GITHUB_TOKEN` |
| `git` | simple-git | local clones under `DEVDIGEST_CLONE_DIR` |
| `codeIndex`, `repoIntel`, `depgraph`, `tokenizer` | ripgrep, repo-intel facade, dependency-cruiser, tiktoken | repo context for prompts |
| `priceBook` | live OpenRouter `/models` prices | falls back to the static `estimateCost` table |
| `embedder()` | OpenAI embeddings | throws unless `EMBEDDINGS_ENABLED=true`, so the app makes zero OpenAI calls by default |

Secrets never live in `AppConfig`. `LocalSecretsProvider` reads
`~/.devdigest/secrets.json` (written from the Settings UI, mode 0600) and falls
back to `process.env`.

Tests pass `ContainerOverrides` (`MockLLMProvider`, `MockGitHubClient`,
`MockGitClient`…) — services depend on the port interfaces, not on the classes.

## Modules

A module is a Fastify plugin under `src/modules/<name>/`:

- `routes.ts` — HTTP surface, zod schemas, `getContext()` for the workspace;
- `service.ts` — use-case logic, talks to the container and the repository;
- `repository.ts` (or `repository/<entity>.repo.ts`) — Drizzle queries.

Some read-only list routes (e.g. `GET /repos/:id/pulls`) still query Drizzle
directly in the route. That is existing drift, not a pattern to copy into new
write paths.

## Background work

- **Review runs** are fire-and-forget: `POST /pulls/:id/review` inserts the
  `agent_runs` rows, returns their ids at once and hands execution to
  `ReviewRunExecutor`. Progress is published on the `RunBus`.
- **RunBus** (`src/platform/sse.ts`) buffers events per run, replays the buffer
  to late subscribers of `GET /runs/:id/events`, supports cancellation, and is
  released on `complete()`. On completion the buffered log is persisted as one
  `run_traces` document.
- **JobRunner** (`src/platform/jobs.ts`) — clone, PR import, indexing and polling
  on a concurrency-limited queue mirrored into the `jobs` table with retries.

## Data

- One table set lives in `src/db/schema/*.ts`; later lessons' tables already
  exist and stay empty until a lesson fills them.
- `agent_runs` is the run timeline (status, tokens, cost, score, blockers);
  `reviews` + `findings` hold the outcome; `run_traces` holds one jsonb document
  per run. `reviews.run_id` has no FK, so deleting a run deletes its review
  explicitly.
- Migrations are generated by drizzle-kit into `src/db/migrations/` and applied
  with `pnpm db:migrate`; the server never migrates on boot.
